## 1. 产品概述

### 1.1 产品定位

建设一套单体酒店内部使用的桌面 Web 运营管理系统，使系统成为酒店在线房态和前台业务的唯一台账，替代 Excel、微信群和人工记忆之间反复核对的工作方式。

第一阶段只服务一家酒店，不实现多租户、SaaS 授权和集团管理，但代码结构应保留未来产品化空间。

### 1.2 核心问题

当前房态依赖 Excel 或微信群同步，预订、排房和入住信息没有唯一可信来源，存在卖重房风险。经营者希望用一套统一系统管理：

- 房型、房间和房价
- 直订预订
- 排房与房态
- 入住与退房
- 押金、房账和收款
- 客房清洁
- 班次交班和日报
- 用户权限和操作审计
- 数据备份和恢复

### 1.3 产品目标

1. 所有有效预订只存在于一个房态台账中。
2. 同一房间在相同日期范围内不能被系统重复分配。
3. 前台能够在 3 分钟内完成标准入住。
4. 房态变更在局域网内 15 秒内完成同步。
5. 每日营收和班次结算不再依赖人工汇总 Excel。
6. 本地服务器故障时，数据丢失不超过 15 分钟，并在 4 小时内恢复。

### 1.4 成功指标

| 指标 | 目标值 | 验收方式 |
| --- | --- | --- |
| 系统内重复分配 | 连续 30 天为 0 | 数据库冲突记录与审计日志 |
| 新直订录入率 | 100% | 一周现状记录与现场抽查 |
| 标准入住耗时 | 不超过 3 分钟 | 现场计时抽样 |
| 房态同步时间 | 不超过 15 秒 | 局域网操作测试 |
| 每日对账 | 不再手工汇总 Excel | 日报与班次结算结果 |
| 系统可用性 | 不低于 99.5% | 运行监控与故障记录 |
| 数据恢复点 RPO | 不超过 15 分钟 | 备份记录 |
| 数据恢复时间 RTO | 不超过 4 小时 | 恢复演练 |

## 3. 产品范围

### 3.1 第一版范围

- 基础资料：酒店、员工、角色、房型、房间、税率
- 预订：到店、电话、微信、查询、创建、修改、取消、未到店
- 排房：必须指定具体房间，日期重叠时禁止保存
- 前台：散客建单入住、预订入住、续住、提前退房、换房
- 房态：占用状态、清洁状态、可用状态分维度管理
- 客房：退房清洁任务、清洁、查房
- 账务：价格、押金、房费、消费、收款、退款、挂账、余额
- 班次：交班结算、支付方式汇总、差异说明和经理确认
- 报表：日报、营收、房态、班次结算和操作审计
- 系统：账号权限、加密、审计、备份和恢复

### 3.2 明确不做

- 移动端 App、移动端网页和清洁人员手机端
- 多酒店、多租户、SaaS 授权和集团管理
- OTA、携程、美团、飞猪和渠道管理器
- 公安旅业系统对接、身份证读卡器和证件照片
- 税控发票开具
- 会员积分、等级、储值和营销
- 餐饮、SPA、会议室、库存和采购
- 团队主单、联房、统一结算和旅行团
- 钟点房、日用房和按时计费
- 动态收益定价和复杂促销
- 自动夜审和自动取消收费
- 人脸识别、智能门锁和机器人服务

## 4. 用户与权限

| 角色 | 主要职责 | 关键限制 |
| --- | --- | --- |
| 管理员 | 系统配置、账号、备份、恢复和全部数据 | 不用于日常前台操作 |
| 经理 | 改价、退款、挂账、差异确认、例外审批 | 敏感操作必须重新认证 |
| 前台 | 预订、排房、入住、退房、收款、交班 | 不能退款、改价或清除差异 |
| 财务 | 对账、报表、收款核对和账务修正 | 财务可由经理兼任，但审计上区分操作人 |

### 4.1 权限原则

1. 每个自然人员工使用独立账号，不允许共用。
2. 角色权限必须由后端校验，前端隐藏按钮不作为安全措施。
3. 创建预订、价格修改、退款、挂账、房态调整和班次确认都记录审计日志。
4. 关键操作记录操作人、审批人、时间、对象、修改前后值和原因。
5. 已入住的订单不得直接取消，必须先退房。
6. 退款、挂账、强制结束班次和清除差异必须由经理重新认证。

## 5. 核心业务流程

### 5.1 创建直订

1. 宾客通过到店、电话或微信提出入住需求。
2. 前台查询日期范围内的可用房间。
3. 前台选择具体房型、房号、入住日期、离店日期和房价。
4. 系统执行房间日期重叠校验。
5. 前台记录来源、宾客信息、担保状态、定金和备注。
6. 校验通过后订单进入“已确认”，房间在该日期范围内被锁定。
7. 任何价格修改或例外都必须由经理重新认证。

### 5.2 办理入住

1. 前台通过姓名、手机号、证件或订单号查询预订。
2. 系统检查订单为“已确认”、房间可用、证件信息完整。
3. 前台确认押金；押金可以为零，但必须记录确认人和确认时间。
4. 系统将订单改为“已入住”，将房间占用状态改为“在住”。
5. 散客支持在同一流程内完成“创建订单 + 办理入住”。

### 5.3 在住期间操作

- 续住：新增日期必须重新检查冲突。
- 提前退房：更新实际离店日期并重算已入住房费。
- 换房：原房间释放，新房间执行冲突校验。
- 增加消费：记录消费项目、金额、发生时间和经办人。
- 补收押金：生成独立收款记录。
- 退款：必须由经理重新认证并记录原因。
- 已入住订单不可直接取消。
- 所有房态和日期变化都写入状态历史。

### 5.4 办理退房

1. 前台查询在住订单并确认没有未录入消费。
2. 系统判断房账是否结清或已获得经理挂账审批。
3. 客房完成查房，确认无物品损坏和未申报消费。
4. 系统完成结算，订单转为“已完成”。
5. 房间占用状态转为“空闲”，清洁状态转为“待清洁”。
6. 系统生成退房清洁任务。

### 5.5 客房清洁与查房

1. 退房后自动生成“退房清洁”任务。
2. 清扫人员完成清扫后，清洁状态改为“已清洁”。
3. 主管查房通过后，清洁状态改为“已查房”。
4. 只有“已查房 + 可正常使用 + 未被预订或占用”的房间才能重新售卖。
5. 清洁任务记录任务类型、房间、操作人、完成时间和状态。

### 5.6 班次结算

1. 系统按班次汇总现金、微信、支付宝和银行卡的收款与退款。
2. 前台输入实际现金盘点金额。
3. 系统计算应收、实收和差异。
4. 存在差异时，前台必须填写原因。
5. 经理确认差异后才能结束班次。
6. 未完成的入住、退房、清洁任务、异常订单和宾客问题必须进入交班记录。

### 5.7 营业日和日报

1. 使用自然日作为基础营业日。
2. 每日 02:00 生成前一日营收、房态、房账和差异日报。
3. 夜班可以继续办理业务。
4. 08:00 由授权人员确认日报并关闭前一个营业日。
5. 关闭后，普通用户不得修改已关闭营业日的账务；经理修正必须生成审计记录。

## 7. 状态模型

### 7.1 订单状态

```text
已确认 -> 已入住 -> 已完成
   |          |
   |          +-> 不允许直接取消；必须先退房
   +-> 已取消
   +-> 未到店
```

- 已取消和未到店为终止状态。
- 第一版不支持重新激活终止订单，需要重新创建订单。
- 订单不得物理删除。
- 所有状态变化记录操作人、时间、原因和前后状态。

### 7.2 房间状态

| 维度 | 状态 | 说明 |
| --- | --- | --- |
| 占用状态 | 空闲 | 当前没有有效占用 |
| 占用状态 | 已锁定 | 已被未来预订锁定在特定日期 |
| 占用状态 | 在住 | 当前有宾客入住 |
| 清洁状态 | 待清洁 | 退房后或保洁前 |
| 清洁状态 | 已清洁 | 清扫完成，尚未查房 |
| 清洁状态 | 已查房 | 主管验收通过，可出售 |
| 可用状态 | 可正常使用 | 可参与正常库存 |
| 可用状态 | 停用维修 | 不参与可售库存，已有预订必须迁移 |

### 7.3 可售条件

房间同时满足以下条件才可出售：

- 可用状态为“可正常使用”
- 清洁状态为“已查房”
- 目标日期范围内没有被其他有效订单锁定
- 目标日期范围内没有被在住订单占用

### 8.1 交互原则

1. 主要业务优先使用列表 + 详情抽屉，不频繁跳转页面。
2. 创建订单、入住和退房使用明确的分步流程。
3. 任何冲突必须显示具体房间、日期和冲突订单。
4. 金额、日期和证件号码使用等宽数字显示，避免误读。
5. 敏感操作必须二次认证，按钮文案明确写出结果。
6. 删除、取消、退款、停用房间和关闭营业日必须二次确认。
7. 失败表单保留输入内容，并在对应字段附近显示错误。


## 8.2 原型方向确认

原型方案已经过初步确认，最终采用混合方向：

- 以“方案 A：值班控制台”为主框架，房态矩阵是首页核心。
- 吸收“方案 B：宾客旅程”的今日时间线，用于表达交班、到店和清洁节奏。
- 吸收“方案 C：客房台账”的右侧详情面板，用于在不跳页的情况下完成订单、房客和房账操作。
- 第一版不采用纯看板作为主导航，也不采用全表格台账作为首页。

## 9. 技术方案

### 9.1 技术栈

| 层级 | 技术 |
| --- | --- |
| 前端 | Vue 3 + TypeScript + Vite |
| 后端 | Java 21 + Spring Boot 4.1 + Spring Security |
| 数据访问 | Spring Data JPA |
| 数据库 | MySQL 8 |
| 部署 | 独立迷你服务器 + UPS，局域网浏览器访问 |
| 备份 | MySQL 本地备份 + 加密外置硬盘 + 云对象存储 |
| 监控 | 服务存活、备份结果、磁盘空间和异常日志 |

### 9.2 逻辑架构

```text
前台电脑浏览器
      |
      | HTTPS / 局域网
      v
Spring Boot 应用
      |
      +-- MySQL 8
      +-- 定时任务
      +-- 审计日志
      +-- 备份任务
              |
              +-- 外置硬盘
              +-- 加密云端备份
```

### 9.3 部署原则

- 第一版按一名并发用户设计，但后端必须使用数据库事务处理冲突，不能依赖单用户假设。
- 前台电脑只运行浏览器，不保存业务数据库。
- 服务器和 UPS 放置在锁柜或限制访问区域。
- 管理员远程访问只能在 VPN 内进行；是否开放远程访问待确认。
- 系统不提供离线客户端。服务器故障时使用人工应急流程，恢复后补录并审计。

### 10.1 数据规则

1. 订单、账务、退款和审计日志不得物理删除。
2. 金额统一使用 `DECIMAL(12,2)`，禁止使用浮点数。
3. 日期范围统一采用 `[checkIn, checkOut)`，即离店日不计入占用。
4. 数据库必须对房间日期区间建立重叠保护。
5. 房型价格只影响未确认的报价；历史订单必须保存成交价格快照。
6. 税率变更不得反向修改历史订单。
7. 手机号和证件号必须使用应用层加密，密钥与数据库分离保存。
8. 数据库备份不得与加密密钥存放在同一位置。

## 12. 验收范围

### 12.1 业务验收

- 40 间房全部录入且房型映射正确。
- 所有未来有效预订完成迁移或补录。
- 到店、电话和微信订单 100% 可在系统中查询。
- 系统内连续 30 天无重复分配。
- 入住、续住、提前退房、换房、退款和挂账流程通过现场测试。
- 班次结算结果与经办人员手工核算结果一致。
- 02:00 日报和 08:00 营业日关闭流程通过测试。

### 12.2 技术验收

- 常规业务页面在局域网内的操作响应不超过 1 秒。
- 两名模拟用户同时提交重叠房间订单时，仅一笔成功。
- 服务重启后未结订单、房态和账务保持一致。
- 模拟数据库损坏后，可在 4 小时内完成恢复。
- 敏感字段在数据库和备份文件中不可直接读取。
- 普通前台账号无法调用退款、改价、挂账和清除差异接口。

### 12.3 现场试运行

- 新旧流程并行运行 2 周。
- 试运行期间系统为主台账，Excel 和微信群只用于核对。
- 每日记录系统问题、人工绕过点和账务差异。
- 严重问题修复后重新开始 30 天稳定性观察。
- 只要发生系统内重复分配，30 天观察期重新计算。
